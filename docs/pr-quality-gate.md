# Whole-candidate PR quality check

`SonarQube / whole-candidate` is a custom commit status, not native SonarQube pull-request analysis. Community Edition does not provide native PR diffs/decoration here. Each validated hosted test candidate (including a proven coverage-threshold-only failure) gets a **new, dedicated project** and an analysis bound to its exact head SHA. The shared application analysis is never overwritten.

## Two separate trust domains

1. `.github/workflows/pr-quality.yml` runs on GitHub-hosted Linux: one job, Node 22.22.0, pinned pnpm 12.18.0, full Vitest suite with real V8/LCOV coverage, typecheck and lint. Actions are pinned to immutable commits. It has contents-read only, no Sonar/SSH/runtime secrets, no OIDC, no self-hosted runner, no deployment. Obsolete PR runs are cancelled. The collector records the original Vitest exit without overriding any coverage threshold. A separate validator requires a complete JSON test report, all assertions/suites passed, no skipped/pending/todo tests, an explicit runtime reporter proving zero unhandled errors, and source-bound LCOV. JSON alone is insufficient: Vitest 4's JSON success flag omits unhandled errors. Exit 1 is accepted for collection **only** with the exact 80% global line-threshold diagnostic, matching the measured LCOV percentage, and no other stderr. Missing/partial reports, unknown errors or other exit codes stop the job. Types and lint must then pass before uploading only authentic LCOV and SHA/repository/run binding, with one-day retention. The final `Enforce coverage threshold` step restores the original negative decision: a coverage-only job stays **red**, never green.
2. An operator-installed, reviewed Python worker polls open PRs to `main` every two minutes. It validates the exact head/repository/event/workflow/run attempt and artifact digest. It fetches the exact public head with no checkout hooks and uses Git object reads to copy application source; it never installs candidate dependencies or executes candidate scripts/tools. The candidate's workflow **and `tools/pr_gate/gate.py` validator** must byte-match the separately installed approved files. The worker queries authenticated `actions/runs/{id}/attempts/{attempt}/jobs`, requires exactly the expected job, matching run/attempt/SHA, and all named phases completed successfully except the final coverage enforcement step, which alone may fail. Unknown/duplicate/missing steps or failing post-action cleanup are rejected. The only allowed skipped step is optional `Post Setup Node` on the red coverage-only job: the pinned action declares `post-if: success()`. Candidate artifact metadata alone cannot authorize a failed run. Workflow/validator changes require explicit operator review and installation; a PR cannot update the trusted worker.
3. The static scanner is a reviewed, immutable ARM-capable image containing `@sonar/scan` 5.1.0. It runs nonroot with read-only root/source/config, no capabilities, resource limits, no Docker socket, no home/SSH/email/runtime credential mounts. Only the source, real LCOV, project-scoped expiring analysis token, and writable analysis output are exposed. Trusted scanner/analyzer binaries may execute from private tmpfs; candidate executables/configs do not. The global API token stays outside the scanner. The scanner uses host networking to reach an existing loopback-only SSH tunnel; this is not network isolation against a scanner vulnerability. Keep the image/server patched.

The application analysis scope is all `src/` files with TS/TSX/JS/JSX/CSS/HTML suffixes, not only changed lines. JSON, candidate tsconfigs, scanner properties, package metadata, scripts, dependencies and Git configuration are not mounted. Tests outside `src/` run in the hosted test phase, not as production code in Sonar. Changes to application source roots/languages require an operator-reviewed scope change. This check is not a claim that Dockerfiles, arbitrary build scripts or every repository file have been statically analyzed.

Forks are eligible under the same rules, but GitHub may require a maintainer to approve a fork's first hosted run. Waiting, missing or cancelled CI is not green. Failed CI is scan-eligible only for the verified coverage-only phase pattern, and the worker additionally records `vitest_lines` as a policy failure even if Sonar's different coverage measure passes. Tests and their coverage are still PR-authored code: structural artifact validation is not proof that a malicious contributor did not deliberately falsify test results. Review test/coverage changes as code; do not treat coverage as a security attestation.

## Policy and its derivation

Read-only discovery of the existing approved `Sonar way` gate found:

| Existing new-code condition | Trusted whole-candidate equivalent |
| --- | --- |
| `new_violations > 0` fails | total `violations` must be 0 |
| `new_coverage < 80` fails | total Sonar coverage must be at least 80% |
| `new_duplicated_lines_density > 3` fails | total duplication must be at most 3% |
| `new_security_hotspots_reviewed < 100` fails | every hotspot must be reviewed |

Additionally reliability, security and maintainability ratings must all be A (`1`). Missing/nonfinite metrics fail. A missing reviewed-hotspots percentage is allowed **only** when the separately returned total hotspot count is exactly zero. No shared server gate/profile/threshold was changed. Sonar's displayed new-code gate is not used to manufacture a first-analysis pass; the worker evaluates whole metrics itself.

Coverage is Sonar's combined line/condition measure, not merely Vitest's line percentage. The existing Vitest 80% line threshold is retained too. These checks can legitimately fail an existing baseline. A locally isolated run of public main `b4c903cd04d7e08ff35f663d9c219574fad49bb5` executed all 146 tests across 20 files, and typecheck/lint passed. Real V8 line coverage was **60.27%**, failing 80%. A separate exact-revision static canary reported **59.7% Sonar coverage**, **0.6% duplication**, **C reliability**, A security/maintainability, **9 violations** and **0 hotspots**. This is a failing local baseline canary, not hosted PR eligibility proof. Remediation is separate work; do not lower thresholds or fabricate LCOV to activate enforcement.

## Fail-closed operation

- ZIP members are exactly `lcov.info` and `binding.json`; duplicates, traversal, symlinks, encrypted/oversize data and mismatched run/SHA/repository are rejected. LCOV paths must exist in the candidate, with valid line bounds and totals.
- A scan must have a successful compute task for its new project, exact analysis ID, and exact SCM revision. Measurements are bracketed by analysis-ID/revision readbacks.
- A lock prevents overlapping workers. Receipts are bound to SHA, run ID/attempt and installed worker hash. Cached receipts require a still-present unexpired matching artifact and exact analysis readback; no stale unrelated analysis can green a new head. An expired/deleted artifact requires a new hosted run.
- Before **either** fresh or cached terminal policy publication, the latest same-head CI run/attempt and authenticated phase conclusions are revalidated; the latest run is fetched again after the jobs readback. A queued/running or replacement successful attempt defers the old result to pending; failed/cancelled/invalid current CI cannot inherit an old green. Head/open state is re-read immediately before every status POST. These REST reads and the status POST are not atomic: a head or CI attempt can still change after the final read. A status belongs only to its recorded SHA, never a new head, and the next poll reconciles later same-head reruns.
- CI waiting is pending; failed/cancelled CI is failure; validation/API/scanner errors are error. Sonar findings fail without exposing source snippets. If the worker is unavailable, new heads never receive success; an already-validated unchanged SHA retains its previously published status, as GitHub commit statuses have no expiry.
- Native polling adds approximately two minutes after CI, plus queue/scanner time. No model/LLM runs, public callback endpoint, new cloud provider or privileged PR runner is involved.

Private `state.json` records project/task/analysis IDs, exact SHA, workflow run/attempt, artifact ID/digest, whole metrics and failed metric names. Unique sanitized JSON reports under `diagnostics/` contain phase, release version, exception class, stable reason, stack locations without locals/messages, mutation uncertainty and exit status. Never publish raw scanner output, tokens or finding snippets. Retain receipts for audit; project/token cleanup must be limited to the worker's exact recorded project names. Do not delete any shared application project. Operators should monitor the user service and diagnose missing artifacts, permissions, expired tokens, changed workflows and scanner/server failures separately from real findings.

## Required owner action (not installed by this change)

After the real PR produces the context, the repository owner must create an **active ruleset for `main`**, with **no bypass actors**, requiring a pull request and required check **`SonarQube / whole-candidate`**, with **Require branches to be up to date before merging**. Block force pushes/deletion. Apply to administrators too; do not grant a bot/direct-push bypass. Also require the hosted `Tests, types, lint and coverage` check from GitHub Actions if selecting both controls.

The current worker posts a user-authenticated REST commit status, not a GitHub App check run. GitHub cannot bind this status to a particular username through `integration_id`; use the context's available source/“Any source”, **not** an invented GitHub Actions binding. Users with repository status-write access can spoof this context. Strong cryptographic producer isolation requires a separately provisioned dedicated GitHub App and owner-selected integration binding; it is not silently provided by this implementation. Owner ruleset enforcement is essential: without it this is advisory, and direct pushes remain possible. The current automation account cannot administer this ruleset.
